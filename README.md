# Zero Defect Space

Работающий демонстрационный контур контроля качества деталей на **синтетических данных**. Он принимает структурированные события внешнего анализа, хранит исходные сообщения, показывает хронологию изделия, формирует случаи несоответствия, принимает решения контролёра, считает базовые показатели и отправляет результаты в отдельный HTTP-эмулятор. Это не система промышленного допуска деталей.

## Быстрый запуск

Нужен Python 3.12+ и пакет из `requirements.txt`. В чистом окружении:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m qc.demo
```

Откройте адрес, напечатанный демосервером, и введите напечатанный `Viewer token` или `Controller token`. Демо содержит четыре изделия, два участка, двух операторов, входной дефект, новый признак после операции, непригодный результат контроля, предупреждение станка и действие оператора. Ожидаемые показатели: **3** проверенных изделия, **2** с подтверждённым несоответствием, **1** без пригодного контроля. Обзор линии отдельно показывает I-004: нет пригодного контроля в срок. В карточке видны контрольная точка и история оповещения. Демо запускает отдельный HTTP-эмулятор, импортирует четыре задания и получает ACK для двух исходящих решений; статусы видны на экране. Подтверждения в демо созданы условным контролёром, не реальным экспертом. Данные и ключ шифрования живут только в процессе; завершение демосервера удаляет их из памяти.

Проверяемые варианты S1–S12 и соответствующие тесты перечислены в [матрице сценариев](docs/SCENARIO_MATRIX.md). В UI исходный маршрут S1–S5; дополнительные S6–S12 воспроизводятся тестами на изолированных экземплярах, чтобы эталонные показатели не изменялись.

Если браузерный smoke-тест доступен, запустите демо с `QC_DEMO_VIEWER_TOKEN=browser-view-token`, затем `node tests/browser_smoke.js` при установленном Playwright. На этой машине Playwright использует `QC_BROWSER_PATH` к установленному Chrome и `NODE_PATH` к пакетам рабочего окружения; это не требование обычного запуска.

## Постоянное локальное хранилище и API

Для отдельного сервера задайте `QC_ENCRYPTION_KEY` (base64 от 32 случайных байтов), уникальные `QC_SOURCE_TOKEN`, `QC_VIEWER_TOKEN`, `QC_CONTROLLER_TOKEN`, `QC_ADMIN_TOKEN` и `QC_DB_PATH`; затем `python -m qc.server`. Не храните ключи и токены в репозитории. Сервер по умолчанию слушает только `127.0.0.1:8765` и **не предоставляет TLS**. Не выставляйте этот режим в сеть предприятия.

Главные ручки описаны в [API.md](docs/API.md). `POST /api/events` отвечает `202` для применённого, помещённого в карантин или повторного сообщения; тело ответа обязательно содержит `state`. Конфликт того же `source_id/event_id` с иным содержимым даёт `409` и запись о конфликте. Решение требует роли controller/admin, ожидаемой версии карточки и ключа идемпотентности.

## Двусторонний эмулятор

Второй процесс `python -m qc.emulator` запускается с `QC_INTEGRATION_TOKEN` на `127.0.0.1:8766`. С тем же токеном и теми же настройками основного хранилища:

```powershell
python -m qc.bridge pull
python -m qc.bridge push
```

`pull` принимает синтетические задания с внешними ID. `push` отправляет ожидающие результаты. `POST /control/fail-next` у эмулятора вызывает однократный отказ `503`; следующий `push` повторяет тот же `message_id` и получает ACK. Проверка этого сценария автоматизирована в `tests/test_bridge.py`. Это **проектный HTTP-контракт**, а не проверенная совместимость с 1С или «Галактика:ERP».

## Что ещё не готово

В рамках текущего контура реализованы: кодогенерация контрактов (`contracts/`), аудит рассинхронизации, долгосрочная криптозащита (включая гибридный KEM), бенчмарк масштабируемости (>1400 оп/сек), устойчивость к сбою воркеров, OPC-UA/ЧПУ и ERP/CAD адаптеры (`qc/adapters/`), edge-буфер store-and-forward (`qc/edge.py`), фоновый планировщик контрольных точек, неизменяемая цепочка хэшей аудита и Docker-окружение (`Dockerfile`, `docker-compose.yml`).

Вне текущего скоупа остаются: физическое развёртывание на реальной линии цеха РКК «Энергия», промышленные камеры машинного зрения, глубокая аналитика по сменам на многолетних архивах и полноценный кластер PostgreSQL/Kafka. Подробное соответствие критериям приведено в [аудите критериев](docs/CRITERIA_AUDIT.md), профили интеграции — в [INTEGRATION_PROFILES.md](docs/INTEGRATION_PROFILES.md), регламент защиты — в [DEFENSE_SCRIPT_4MIN.md](demo/DEFENSE_SCRIPT_4MIN.md).
