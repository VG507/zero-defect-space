# Zero Defect Space

Работающий демонстрационный контур контроля качества деталей на **синтетических данных**. Он принимает структурированные события внешнего анализа, хранит исходные сообщения, показывает хронологию изделия, формирует случаи несоответствия, принимает решения контролёра, считает базовые показатели и отправляет результаты в отдельный HTTP-эмулятор. Это не система промышленного допуска деталей.

Трассировка демонстрирует состав изделия из `AssemblyImported`, снятие/установку компонента в I-005, привязку наблюдения к `component_id` и `operation_run_id`, а также операторов, оборудование, интервалы операций, исходные факты и отдельные решения. Сопоставление по времени не устанавливает причину дефекта. Компонентные данные и идентификаторы условные; реальные спецификации сборок и технологические маршруты не проверены.

## Быстрый запуск

Нужен Python 3.12+ и пакет из `requirements.txt`. В чистом окружении:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m qc.demo
```

Откройте адрес, напечатанный демосервером, и введите один из напечатанных `Viewer token`, `Controller token` или `Admin token` в поле «Токен роли». Для проверки журнала войдите с `Admin token` и нажмите «Проверить журнал» внизу страницы. Демо содержит **шесть изделий**: I-001–I-004 показывают базовый маршрут, I-005 — повторную обработку после решения, I-006 — поздний входной факт и пересмотр без потери решения. Ожидаемые показатели: **5** проверенных изделий, **3** с последним решением `confirmed`, **1** без пригодного контроля. Для I-005 прежнее подтверждение остаётся в истории, а текущее решение требует дополнительной проверки; I-006 имеет последнее решение `confirmed`, но помечено к пересмотру. Демо импортирует четыре задания из отдельного HTTP-эмулятора, добавляет два локальных синтетических задания и получает ACK для пяти исходящих решений. Подтверждения в демо созданы условным контролёром, не реальным экспертом. Данные и ключ шифрования живут только в процессе; завершение демосервера удаляет их из памяти.

| Роль | Что разрешено |
|---|---|
| `viewer` | Смотреть изделия, историю, показатели и исходящие результаты; не менять данные. |
| `controller` | Всё доступное `viewer` и фиксация решения по случаю с указанием автора и основания. |
| `admin` | Просмотр, решения, приём событий, сканирование контрольных точек и проверка целостности журнала. |
| `source` | Только приём одиночных событий и пакетов через API; этот токен в демо-консоль не выводится. |

Вывод `Admin token` предназначен только для локального синтетического демо: не публикуйте его вместе с логом запуска. Обычный сервер `qc.server` токены не печатает; для него они задаются переменными окружения.

В начале демо проверка целостности охватывает **39 исходных событий**: 4 импортированных задания и 35 локально созданных событий сценариев, включая состав изделий и снятие/установку компонента. Решения контролёра и ACK не входят в эту проверку. Admin-экран отдельно показывает проверку содержимого, связности хэшей и локального HMAC-якоря. После отправки новых событий счётчик растёт.

Проверяемые варианты S1–S12 и соответствующие тесты перечислены в [матрице сценариев](docs/SCENARIO_MATRIX.md). В UI исходный маршрут S1–S5; дополнительные S6–S12 воспроизводятся тестами на изолированных экземплярах, чтобы эталонные показатели не изменялись.

Если браузерный smoke-тест доступен, запустите демо с `QC_DEMO_VIEWER_TOKEN=browser-view-token`, затем `node tests/browser_smoke.js` при установленном Playwright. На этой машине Playwright использует `QC_BROWSER_PATH` к установленному Chrome и `NODE_PATH` к пакетам рабочего окружения; это не требование обычного запуска.

## Постоянное локальное хранилище и API

Для отдельного сервера задайте `QC_ENCRYPTION_KEY` (base64 от 32 случайных байтов), уникальные `QC_SOURCE_TOKEN`, `QC_VIEWER_TOKEN`, `QC_CONTROLLER_TOKEN`, `QC_ADMIN_TOKEN` и `QC_DB_PATH`; затем `python -m qc.server`. Не храните ключи и токены в репозитории. Сервер по умолчанию слушает только `127.0.0.1:8765` по HTTP; для TLS передайте одновременно `--ssl-cert` и `--ssl-key` или соответствующие переменные окружения. Неверная пара TLS-файлов останавливает запуск. Не выставляйте HTTP-режим в сеть предприятия. Файл `<QC_DB_PATH>.audit-anchor` необходим для проверки удаления конечных записей; резервируйте его отдельно от БД. Непустая база без якоря не открывается автоматически.

Главные ручки описаны в [API.md](docs/API.md). `POST /api/events` отвечает `202` для применённого, помещённого в карантин или повторного сообщения; тело ответа обязательно содержит `state`. Конфликт того же `source_id/event_id` с иным содержимым даёт `409` и запись о конфликте. Решение требует роли controller/admin, ожидаемой версии карточки и ключа идемпотентности.

Для массового приёма `POST /api/events/batch` принимает массив из 1–100 событий, фиксирует его одной SQLite-транзакцией и обновляет якорь не более одного раза; ответ содержит отдельный статус каждого события. Прямой in-process бенчмарк `EventStore` на локальном наборе из 600 событий и одном потоке: размер пакета 50 дал 1235.7 событий/с против 32.2 по одному. Это измерение конкретной машины, а не гарантия скорости HTTP-транспорта, другого оборудования или масштабирования по потокам.

## Двусторонний эмулятор

Второй процесс `python -m qc.emulator` запускается с `QC_INTEGRATION_TOKEN` на `127.0.0.1:8766`. С тем же токеном и теми же настройками основного хранилища:

```powershell
python -m qc.bridge pull
python -m qc.bridge push
```

`pull` принимает синтетические задания с внешними ID. `push` отправляет ожидающие результаты. `POST /control/fail-next` у эмулятора вызывает однократный отказ `503`; следующий `push` повторяет тот же `message_id` и получает ACK. Проверка этого сценария автоматизирована в `tests/test_bridge.py`. Это **проектный HTTP-контракт**, а не проверенная совместимость с 1С или «Галактика:ERP».

## Что ещё не готово

В текущем контуре реализованы: кодогенерация схемных типов и CI-проверка (`contracts/`, `.github/workflows/verify.yml`), шифрование AES-GCM и опциональный гибридный профиль ML-KEM-768/X25519, локальный аудит с отдельным HMAC-якорем, тест аварийного завершения процесса, SQLite edge-буфер с повторной отправкой, фоновый контроль точек, адаптеры преобразования данных и Docker-конфигурация. `scripts/benchmark_load.py` измеряет конкретный запуск, но **не доказывает** масштабирование SQLite; OPC-UA и ERP-профили не испытаны на реальных системах. `scripts/run_screencast_demo.py` записывает WebM при установленном Playwright с FFmpeg. Контейнерный запуск требует проверки на машине с Docker daemon.

В интерфейсе есть пульт перехода по шести уже загруженным сценариям, печатный **демонстрационный отчёт прослеживаемости** и экран текущих ответов сервера/эмулятора. Для события контроля источник может передать JPEG/PNG до 256 КиБ; снимок показывается в истории как материал источника, **без компьютерного анализа и подтверждения подлинности**. Проверку целостности из интерфейса может запускать только роль `admin`. Эти экраны не создают официальный паспорт качества и не дают автоматического допуска.

Вне текущего скоупа остаются: физическое развёртывание на реальной линии цеха РКК «Энергия», промышленные камеры машинного зрения, глубокая аналитика по сменам на многолетних архивах и полноценный кластер PostgreSQL/Kafka. Подробное соответствие критериям приведено в [аудите критериев](docs/CRITERIA_AUDIT.md), профили интеграции — в [INTEGRATION_PROFILES.md](docs/INTEGRATION_PROFILES.md), маршрут 7-минутной демонстрации — в [DEFENSE_SCRIPT_7MIN.md](demo/DEFENSE_SCRIPT_7MIN.md).
