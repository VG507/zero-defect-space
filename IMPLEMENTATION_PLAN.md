## 1. Цель, границы и порядок приоритетов

Цель демо: провести несколько условных изделий через входной контроль, минимум два участка и две операции, принять результаты внешнего анализа и события станка/оператора, построить единую историю, зарегистрировать случаи несоответствия, дать контролёру принять решение, пересчитать показатели и отправить результат в эмулятор внешней системы. Любой вывод должен быть прослеживаем до исходных событий.

Целевой результат — одновременно работающий MVP и архитектурное описание. ТЗ допускает только одну из этих сущностей, но прямо называет обе целевым образом. Рекомендуется сначала обеспечить сквозной работающий сценарий, затем оформить его как основу целевой архитектуры.

Границы MVP:

- Входом являются структурированные сообщения от условных VisionQC, OperatorVision, MachineLogs и производственных систем. Обучение собственной CV-модели, реальное подключение камер и доступ к реальным данным не требуются.
- Фото/видео факультативны. Пустая ссылка или заглушка не показывается как доказательство.
- Для реального обмена достаточно двустороннего эмулятора. Контракты целевых 1С, Галактика:ERP, MES и КОМПАС-3D описываются без заявлений о проверенной совместимости.
- Predictive, расширенная Simulation и MobileOps показываются в архитектуре; их программная реализация необязательна.
- Для размеров, допусков и качества соединений нельзя утверждать достоверность по одной условной видеокартинке; требуются калибровка и, возможно, дополнительные средства контроля.

Приоритеты:

| Уровень | Результат | Причина |
|---|---|---|
| P0 | Сквозная история, статусы, решения, повтор/задержка, демонстрационный набор | Ядро кейса и две наиболее весомые отраслевые строки критериев |
| P1 | Эмулятор с обменом в обе стороны, защита, аналитика, работающий интерфейс, воспроизводимый запуск | Обязательные пункты ТЗ и технические баллы |
| P2 | Полный проект камер/ИИ, адаптация к данным заказчика, контракты целевых систем, документация и скринкаст | Показывает применимость на производстве |
| P3 | Нагрузочная демонстрация, единая спецификация с генерацией, автоматические проверки несовместимости | Дополнительные баллы при наличии времени |
| P4 | Реализованный проверяемый гибридный/постквантовый криптосценарий | Дополнительный критерий с высокой ценой ошибки |

Нельзя заявлять о промышленной точности, гарантированном предотвращении брака, подтверждённой вине оператора или проверенной совместимости с системами предприятия на основе синтетического демо.

Ключевые интерфейсы должны оставаться малыми: приём нормализованного события, чтение истории изделия, запись решения, чтение показателей, постановка исходящего сообщения. Их обязательные поля, инварианты и ошибки документируются. Для подмены хранилища, транспорта и интеграции нужны отдельные адаптеры только в местах реальной изменчивости.

Источник достоверности: исходное сообщение фиксирует полученное системой утверждение и его происхождение; подлинность источника устанавливается отдельной проверкой. Справочник изделий/сборок приходит из выбранной внешней системы; решение о подтверждении/отклонении принадлежит контролёру; производные истории и показатели вычисляются системой. При конфликте справочников система показывает источник, время и состояние согласования, а не тихо выбирает значение.

Горизонтальное масштабирование: обработчики могут работать параллельно по разным item_id; для одного изделия требуется сериализация на уровне транзакции/блокировки или последовательного ключа. Вся рабочая информация, нужная для восстановления, находится в БД. Повторная обработка события идемпотентна. Добавление копий сервера само по себе не подтверждает масштабируемость: демонстрируются 1 и N обработчиков, задержки, полнота и отсутствие дублей.

Вертикальное масштабирование: отдельно описать CPU/память обработчиков, размер пула соединений, лимиты пакета, индексы и ресурсы БД; сравнивать нагрузку при фиксированном сценарии. Возможные узкие места — транзакции по одному изделию, повторная сборка длинной истории, общая БД, экспорт во внешнюю систему и глобальный журнал целостности. Если цепь целостности сериализует все записи, выбрать сегменты/периоды с проверяемым закреплением корней и документировать гарантию.

Путь к Kafka: добавить транспортный адаптер публикации/чтения и настройки; сохранить версионированный конверт события, ключ партиции item_id, идемпотентную обработку и replay; проверить обработку повторов, перестановок, восстановления и границы доставки. Бизнес-правила и модель случаев остаются внутри ядра.

Путь к OpenTelemetry: внедрить интерфейс телеметрии в точках приёма, обработки, проекции, решения и интеграции; добавить конфигурацию экспортёра, метрики задержки/ошибок/очереди и трассировку по correlation_id без утечки содержимого защищённых событий; проверить наблюдаемость отказа и восстановления.

## 4. Модель данных и инварианты

### 4.1. Справочники и производственная структура

- item_type: тип детали/изделия и версия описания.
- item: уникальный экземпляр, тип, серийный/условный ID, стадия жизненного цикла.
- assembly_version: ID и версия сборки, ссылки на компоненты, количество и тип связей. В условном файле отсутствие геометрии фиксируется явным признаком.
- item_component: конкретный компонент конкретной сборки; связи не должны подменять историю экземпляров.
- line, station, operation_definition, equipment, operator_alias, shift: справочники и их версии; реальные персональные данные не нужны.
- work_order: задание из эмулятора/внешней системы, внешний ID, версия и источник.
- operation_run: уникальный ID каждого исполнения, item_id, операция, участок, оператор/оборудование при известности, начало, паузы, конец, связь с previous_run_id для повторной обработки.

### 4.2. Событийный журнал и интерпретация

- raw_event: идентификаторы источника и сообщения, версия контракта, occurred_at, received_at, исходный зашифрованный payload, digest исходных байтов, контрольная метка и версия защиты; изменение записи запрещено штатными правами. Изменяемое состояние обработки в этой таблице не хранится.
- processing_event: добавляемые записи о проверке, карантине, применении, ошибке и повторе обработки с ссылкой на raw_event.
- ingestion_state: отдельное текущее состояние проверки/обработки, причина карантина или ошибки, попытки и время обновления; это производное представление из processing_event.
- normalized_event: проверенное представление исходного события с ссылкой на raw_event, версией нормализатора и возможными неизвестными значениями.
- unresolved_event: событие, которое нельзя надёжно привязать к изделию/операции/версии; хранит причину и возможность последующей привязки. Не превращается в подтверждённый дефект без основания.
- inspection_observation: результат трёх состояний, quality/confidence при наличии, дефекты как отдельные наблюдения, ссылка на материал при наличии, версия внешнего анализатора.
- defect_case: устойчивый ID рассматриваемого несоответствия; ссылки на наблюдения; текущая производная стадия; решение и причина выводятся из связанных записей.
- cause_assessment: гипотеза/подтверждение причины, альтернативы, недостаток сведений, автор или правило и версия, основание из событий.
- controller_decision: подтверждение, отклонение либо назначение дополнительной проверки; автор, время, мотив и ссылки на основания. Команда порождает неизменяемое событие решения; таблица решений служит читаемым представлением. Новое решение добавляется, старое остаётся в истории.
- action_event и machine_event: действия оператора и состояние оборудования с привязкой ко времени и operation_run_id, если связь надёжна.
- projection_checkpoint: версия правил и позиция обработанных событий; позволяет воспроизвести представления.
- integration_mapping и outbox_message: внешние ID, направление, версия контракта, payload, попытки, подтверждение/ошибка, correlation_id.
- audit_entry: критическое действие, субъект, объект, основание, предыдущий и текущий контрольный идентификатор.

Три независимые плоскости: (1) что источник сообщил, (2) что вычислила система, (3) что решил человек. Интерфейс, журнал и аналитика показывают различие. Любая повторная сборка производных представлений не переписывает источник.

Стабильные связи подтверждать внешними ключами или явными разрешёнными состояниями неизвестности. Уникальные ограничения как минимум: (source_id, event_id) для приёма, operation_run_id для исполнения, (target_id, message_id) для исходящей доставки, (item_id, external_system, external_id) для сопоставления. Версию карточки случая обновлять атомарно для защиты от одновременных решений.

### 4.3. Правила идентичности и дедупликации

Уникальность сообщения задаётся парой (source_id, event_id). Повтор с тем же содержимым возвращает исходный результат без изменения истории и статистики; повтор с тем же ID и иным содержимым получает конфликт и запись для разбора. Один сигнал может содержать несколько типов/областей дефекта, поэтому defect_observation имеет отдельный ID и ссылку на raw_event.

Связь наблюдений с одним случаем: одинаковый item_id, компонент/область, тип дефекта и явный correlation_id либо заданное правило сопоставления; отсутствие надёжного совпадения создаёт отдельный случай с последующей возможностью ручного объединения. Ручное объединение/разделение оформляется новым аудируемым решением. Счётчик «дефекты» и счётчик «изделия с дефектами» считают разные множества.

Идентификатор случая закрепляется при первом наблюдении и хранится отдельно от пересчитываемого состояния. Replay не переименовывает уже опубликованный случай или решение; изменение правила связывания создаёт запись о переносе/объединении с прежними ID.

Повторное исполнение операции всегда новый operation_run_id и previous_run_id. Ручная правка интервала создаёт корректирующее событие с причиной, а не переписывает первоначальное время.

### 4.4. Время и поздние события

Хранить occurred_at, received_at, часовой пояс/смещение источника и указание доверия к его часам. Для длительности хранить значение, единицу и interval_kind: активная обработка, полное время на участке или иной определённый интервал; отдельно отмечать reported или derived. Если начало/конец отсутствуют или часы рассинхронизированы, не выдавать точную производную длительность.

Порядок истории — по occurred_at с устойчивым разрешением совпадений через source sequence или event_id; received_at нужен для объяснения задержки. Позднее событие вызывает повторную сборку представления затронутого item_id, версии аналитики и, при необходимости, исходящего результата. Уже подтверждённое человеком решение не удаляется автоматически; новый факт помечает необходимость пересмотра, если меняет его основание.

Отсутствие события выявлять сравнением ожидаемых контрольных точек маршрута из задания с полученными событиями. До наступления настроенного срока контрольная точка имеет состояние «ожидается»; после срока — «пропуск/нет данных». Срок и версия маршрута отображаются как основание. Пропуск не заменяется искусственным событием о нормальном результате. Если поздний сигнал закрывает пропуск, история пересчитывается, а прежнее предупреждение остаётся в аудите.

### 4.5. Транзакции, replay и границы побочных эффектов

При приёме проверяются подлинность источника и минимальный конверт, затем исходный payload шифруется и сохраняется один раз вместе с ключом дедупликации. Полная проверка версии и содержимого либо переводит запись в очередь применения, либо в карантин с явной причиной. При повторной доставке идентичное сообщение возвращает прежний ingestion_id, а тот же (source_id, event_id) с другими байтами даёт конфликт. API не сообщает об успешном применении события, пока выполнено только его сохранение.

Обработчик берёт одно изделие/ключ маршрутизации, нормализует события и в одной транзакции фиксирует производные записи, контрольную точку обработки и необходимые исходящие сообщения в outbox. Если транзакция не завершилась, событие остаётся ожидающим повторной обработки. При позднем событии обработчик перестраивает представление затронутого изделия по детерминированному порядку и версии правил. Внешний вызов выполняется только после коммита из outbox; повтор вызова несёт тот же message_id.

Команда контролёра проверяет роль и версию карточки, атомарно добавляет событие решения и запись outbox, затем обновляет представление. Двойная команда с одним idempotency key не создаёт второе решение. После нового решения или позднего события внешний результат получает новую версию и связь с прежним отправленным результатом; ранее отправленное сообщение не удаляется. Если позднее событие меняет основания уже принятого решения, автоматическое подтверждение нового вывода не выполняется: случай отмечается для повторного рассмотрения.

## 5. Контракт события и обработка ошибок

Базовый конверт: event_id, event_type, schema_version, occurred_at, source_id, item_id/item_type_id при известности, line_id/station_id, operation_run_id, correlation_id и payload. Принимающая система сама ставит received_at и ingestion_id. Для каждого event_type документировать обязательные поля, типы, единицы, допустимые значения и семантику отсутствующего/неизвестного.

Семейства событий для MVP:

1. WorkOrderReceived и CatalogUpdated.
2. ItemReceived и IncomingInspectionCompleted.
3. OperationStarted, OperationPaused, OperationResumed, OperationFinished и ReworkStarted.
4. InspectionReported с inspection_result = signs_detected / no_signs_detected / unable_to_assess; defects — массив, confidence и observation_quality факультативны.
5. OperatorActionObserved; источник и уверенность действия сохраняются.
6. MachineStateChanged, MachineWarning, MachineStopped.
7. ControllerDecisionRecorded и CauseAssessmentRecorded.
8. AssemblyImported и IntegrationResultAcknowledged/Rejected.

Для демонстрации задать объяснимый, версионированный справочник признаков: например, аномалия сварного шва, царапина, вмятина, отклонение геометрии. Для каждого — где и чем условно обнаруживается (внешний CV-сигнал, измерение или контроль человека), единица/область наблюдения, связь с операцией и возможное состояние «классификация не установлена». Это примеры из обсуждения, а не подтверждённая номенклатура дефектов РКК «Энергия»; производственный допуск/порог без данных заказчика не назначать.

Правила:

- Неизвестная версия конверта: сохранение исходного сообщения в карантине и ответ с кодом неподдерживаемой версии; бизнес-правила его не применяют.
- Новое необязательное поле: допускается документированным правилом совместимости, исходные байты сохраняются.
- Отсутствие обязательного поля или неизвестное значение перечисления: сохранение в карантине и явная ошибка; не подставлять безопасный с виду статус.
- Несовместимое изменение: новая версия контракта и адаптер; версия контракта отдельно от analyzer_version и версии приложения.
- Ошибка проверки идентичности изделия или исполнения: статус «связь не установлена»; на экране нельзя показывать уверенную привязку.
- Отсутствующие события: незавершённая операция/неполная история; отсутствие сообщения о браке не равно подтверждённой годности.
- Подтверждение успешного приёма источнику выдаётся после сохранения входа; бизнес-обработка и исходящая доставка имеют отдельные статусы.
- Для observation_quality использовать документированные good / poor / unknown. При no_signs_detected и poor/unknown изделие не получает статус подтверждённой годности. Если качество не передано, применять unknown; числовой порог confidence без данных заказчика не задавать.

Контракты хранить с примерами успешных и ошибочных запросов/ответов. Для дополнительных баллов: единая схема порождает серверные и клиентские типы; две последовательные версии контракта и проверка устаревших артефактов в CI.

Предлагаемые внешние интерфейсы MVP: приём одного события и пакета; список изделий и история конкретного item_id; список случаев и карточка конкретного case_id; запись решения контролёра; отчёт с фильтрами и определениями показателей; список входящих/исходящих интеграционных сообщений; запрос проверки целостности для уполномоченного пользователя. В спецификации каждого интерфейса указать роль, вход, ответ, статус ошибки, правила повтора, побочный эффект и пример. Критические команды должны принимать idempotency key и ссылку на рассматриваемую версию карточки, чтобы двойной клик и устаревшая вкладка не создавали скрытый конфликт.

## 6. Разбор несоответствий и правила принятия решений

Предлагаемые стадии случая: signal_received → awaiting_review → confirmed / rejected / needs_more_inspection. Причина ведётся отдельно: unknown → hypothesized → confirmed; «подтверждённая ошибка оператора» допустима только отдельным обоснованным решением. Эти имена — проектная схема, не обязательные термины заказчика.

Алгоритм формирования карточки:

1. Сопоставить наблюдение с изделием, компонентом и операцией; при неуверенной связи вывести уровень определённости.
2. Найти последнее подходящее наблюдение до операции, первое после неё, события оборудования и действия в определённом окне; само окно является настройкой с версией.
3. Показать факты, возможные объяснения, альтернативы и пробелы. Например, входной дефект исключает автоматическое приписывание его оператору последующего участка; отсутствие проверки до операции оставляет момент возникновения неизвестным.
4. Создать/обновить производное представление случая без изменения исходных сообщений.
5. Контролёр подтверждает, отклоняет или назначает проверку с мотивом. Изменение мнения — новое решение.
6. Пересчитать производные показатели и подготовить исходящий результат; после позднего события отразить возможную необходимость повторного рассмотрения.

Примеры формулировок в интерфейсе: «признак дефекта обнаружен источником», «несоответствие подтверждено контролёром», «возможна связь с остановкой станка», «причина не установлена». Нельзя автоматически превращать гипотезу в установленный факт.

## 7. Производственная аналитика: точные определения

Для каждого показателя в документации фиксируются множество включаемых записей, знаменатель, статус рассмотрения, временной интервал, версия правил и реакция на позднее событие.

| Показатель | Источник и смысл | Важная проверка |
|---|---|---|
| Проверенные изделия | Уникальные item_id с хотя бы одним пригодным для оценки результатом контроля (signs_detected или no_signs_detected при good) в выбранном интервале | unable_to_assess и poor/unknown показывать отдельно; «проверено» не равно «годно» |
| Изделия с подтверждённым несоответствием | Уникальные item_id со случаем в стадии confirmed | Два дефекта одного изделия дают одно изделие |
| Дефекты по типу/линии/участку | Уникальные подтверждённые случаи/дефекты по документированному правилу связи | Повторные наблюдения не удваивают число случаев |
| Причина установлена/не установлена | Уникальные подтверждённые случаи с отдельным статусом cause_assessment | Гипотеза не считается установленной |
| Входной брак | Случаи с основанием на входном контроле | Не записывать как производственную ошибку |
| Проблемы оборудования | События станка и подтверждённые случаи с отдельной связью | Корреляция по времени не доказывает причинность |
| Длительность | operation_run; reported/derived и interval_kind | Нельзя складывать активное время и полное время участка как одно число |
| Повторная обработка | operation_run с previous_run_id | Не смешивать с повторной доставкой сообщения |
| Подтверждённые ошибки | Только отдельные решения по сопоставимым работам | Группы сравнения должны иметь одинаковые вид операции/тип изделия/условия, насколько данные позволяют |

Отдельные фильтры: период, изделие/тип, линия, участок, смена, оператор, оборудование, стадия случая, источник и качество наблюдения. Дополнительные показатели — ожидание, простой, прохождение контроля с первого раза, задержка обнаружения — выводить лишь при наличии определённых входов.

## 8. Эмулятор и целевые интеграции

### 8.1. Обязательная работающая интеграция

Эмулятор предоставляет задание или справочник с внешним ID, версией и составом изделия; ядро получает данные, сохраняет источник и отображает ID. После решения контролёра ядро отправляет результат контроля из outbox. Для изделия без обнаруженных признаков отдельный результат отправляется после завершения предусмотренных контрольных точек с пригодным качеством наблюдения; формулировка «признаков не обнаружено» не подменяет отдельное решение о допуске изделия. Эмулятор возвращает ACK либо явную ошибку. Для ошибки показать повторную отправку без дублирования. На экране видны идентификатор сообщения, направление, время, результат и число попыток.

Минимальный контракт исходящего результата: message_id, schema_version, work_order_external_id, item_id и внешний ID, итоговый статус, ID решения/его версия, occurred_at/created_at, ссылка на исходные основания, correlation_id. Исходящий результат не должен выдавать непроверенный признак за подтверждённый брак.

### 8.2. Документация целевых адаптеров

| Система | Направление, которое описать | Достоверность и сопоставление |
|---|---|---|
| 1С | Задания/справочники → ядро; статусы/результаты → 1С | Внешний ID и версия, подтверждение, отказ, повтор |
| Галактика:ERP | Задания/справочники → ядро; результаты → ERP | Аналогично, без заявлений о конкретном непроверенном протоколе |
| MES | Операции/маршруты/состояния ↔ производственная история по согласованному контракту | Исключить повторный ручной ввод; определить мастер-источник каждого поля |
| КОМПАС-3D | Сборка → внутренний граф изделия через интерфейс САПР/адаптер | Для MVP разрешён условный файл: ID, версия, компоненты, количество, связи; отсутствие геометрии указать |

Для каждого: направление, пример запроса/ответа, схема, source-of-truth, таблица внешних и внутренних ID, версия, обработка ошибки, повтор, подтверждение, недоступность. Адаптер переводит внешний формат в внутренний; изменение внешнего формата не правит правила качества. Для MES направление подтверждается конкретной схемой предприятия на этапе подключения; двусторонняя стрелка в таблице означает проектную возможность, а не проверенный протокол.

Уточнение экспертной сессии: одних блоков на схеме недостаточно для сильной демонстрации интеграции. В работающем эмуляторе предъявить конкретные HTTP-ручки, тело запроса/ответа и ошибки для получения задания и передачи результата. Для 1С и Галактика:ERP подготовить по отдельному проектному профилю адаптера с названными бизнес-объектами и примерами полей; не утверждать, что эти условные ручки совпадают с интерфейсом реального предприятия. Показать, какие данные остаются в ядре, какие уходят во внешнюю систему и зачем. Реальные версии, конфигурации и протоколы не предоставлены.

## 9. Защита и воспроизводимый аудит

Минимальная модель угроз: ошибочное/несанкционированное изменение записи, подмена источника, повтор сообщения, доступ пользователя к чужой роли, утечка из БД, недоступность ключа, вмешательство в транспорт. Для каждой угрозы документировать защитный механизм и остаточный риск.

Права по ролям для MVP: контролёр читает историю и случаи, записывает решения; мастер читает ход работ и задержки, без подтверждения дефекта; технолог читает обстоятельства и может фиксировать обоснованную гипотезу причины, но не подменять решение контролёра; руководитель читает агрегаты и детали в согласованных пределах; администратор управляет пользователями, источниками и конфигурацией, а его критические действия аудируются. Точные права являются проектным предложением и согласуются с заказчиком.

Реализация MVP:

- Роли: контролёр, мастер, технолог, руководитель, администратор; сервер проверяет права на чтение и критические команды, UI лишь отражает их.
- Исходный payload шифруется аутентифицированным шифрованием с версией формата и key_id. Ключ не хранится в репозитории, БД или демопакете. Отдельные ключи/секреты для шифрования и защиты аудита.
- Запись событий только добавлением; штатный пользователь БД не имеет UPDATE/DELETE на таблицы исходных данных. Коррекция — новое событие.
- Контроль целостности: проверяемая цепь/подпись или код аутентификации для критических записей с внешним по отношению к БД секретом; отдельная проверка неизменности истории. Область гарантии и пределы при компрометации ключей описаны.
- Критические действия имеют автора, роль, время, объект, основание и результат. В демо изменение контрольной записи блокируется либо обнаруживается при проверке.
- Защита передачи при разнесении компонентов, очистка журналов от секретов и сырого содержимого событий; ошибки доступа и подлинности различаются.
- Архитектура резервного копирования и восстановления включает БД, ключи, проверку целостности после восстановления и процедуру проверки replay.

Шифрование, подлинность сообщения и неизменяемость журнала показываются тремя разными проверками. Наличие одного механизма не засчитывается как доказательство остальных.

Дополнительный криптографический критерий после P0–P2: защищённый пакет с version, crypto_profile_id, key_id/key_version, mechanism, открытыми параметрами и source_event_id. Нужны пакеты до и после смены ключа/профиля, изменённый пакет и сценарий отсутствующего ключа. Переход не перезаписывает исходную доказательную историю. Конкретный постквантовый/гибридный профиль выбирать только после проверки библиотечной поддержки и модели угроз; полноценную демонстрацию заявлять лишь при работающей реализации.

## 10. Проект «камеры + ИИ» и адаптация к данным предприятия

Отдельная архитектурная записка описывает:

1. Контрольные точки до и после критических операций, входной контроль, сборка; идентификацию экземпляра и operation_run_id.
2. Расположение камер, ракурсы, свет, помехи, закрытые зоны и физические ограничения наблюдения.
3. Условные классы дефектов и предполагаемые методы; сравнение до/после, события действий и связь с режимами оборудования.
4. Локальную обработку у линии для минимизации передачи и реакции, центральный контур для истории, правил и аналитики.
5. Формат выходного сигнала, confidence/observation_quality, состояние unable_to_assess, потерю связи и повторную доставку.
6. Проектные параметры разрешения, частоты, задержки, нагрузки и минимального обнаруживаемого дефекта с пометкой «требует измерения на производстве».
7. Калибровку и дополнительные измерительные средства для размеров, допусков, скрытых дефектов и качества соединений. Демосценарий не считается промышленной валидацией.

План адаптации к данным заказчика: согласовать доступ и классы дефектов → собрать/обезличить материалы → экспертная разметка/подтверждение → обучение либо настройка правил → проверка на отложенных производственных сценариях → регистрация версий данных, модели и контракта раздельно → согласование допуска → мониторинг качества → откат к предыдущей версии. Человек утверждает неоднозначные выводы и допуск; автоматизация покрывает сбор, проверки формата, расчёт показателей, сравнение версий и журнал изменений.

## 11. Интерфейс и демонстрационный путь

Экран 1, «Линия»: участки, текущие изделия, статус операций, ожидание/ошибки источников, незавершённые и повторные операции, задержки. Не показывать «всё хорошо» при отсутствии сигнала.

Экран 2, «История изделия»: сборка и компоненты, входной контроль, хронология произошедшего/полученного времени, операции и исполнения, действия, станок, результаты, материалы при наличии, внешний заказ. Позднее событие визуально помечается.

Экран 3, «Карточка несоответствия»: исходные наблюдения, качество/уверенность, множественные дефекты, факты до/после, возможные обстоятельства и недостаток сведений, текущая стадия, история решений, кнопки контролёра и основание.

Экран 4, «Аналитика»: обязательные показатели с определением числителя/знаменателя, фильтрами и пометкой «подтверждённое/гипотеза/неизвестно»; раздельно дефекты и изделия с дефектами.

Экран 5, «Интеграции/аудит»: входное задание, исходящий результат, ACK/ошибка/повтор, состояние источников, проверка целостности. Экран может быть частью администрирования, отдельное приложение не требуется.

Основной демомаршрут: импорт задания → приём детали → входной контроль → участок А → участок Б → новый сигнал → карточка с основаниями → решение контролёра → изменение статистики → отправка результата и ACK. Дополнительный маршрут показывает входной брак, неопределённость, повтор, задержку и вмешательство в запись.

## 12. Синтетический набор и ожидаемые результаты

Данные состоят из отдельных файлов справочников, сборок, событий, интеграционных сообщений и ожидаемых результатов. Ожидания не должны храниться внутри входных событий.

| Сценарий | Минимальный вход | Ожидаемое утверждение |
|---|---|---|
| S1 Нормальное производство | Полный маршрут изделия через два участка, несколько хороших наблюдений | Целостная история и длительности с указанным происхождением; нет подтверждённого дефекта |
| S2 Входной дефект | Признак до первой обработки и решение контролёра | Входной брак, без автоматической ошибки оператора |
| S3 Новый дефект | Наблюдение до/после операции, дефект после, действие и/или журнал станка | Случай, факты и возможные обстоятельства; причина остаётся гипотезой до подтверждения |
| S4 Неопределённость | Плохое качество наблюдения, пропущенная проверка или неуверенная связь | unable_to_assess / unknown; нет ложной годности и категоричного обвинения |
| S5 Станок | Предупреждение или остановка во время operation_run | Событие привязано к оборудованию и операции; причинность не утверждается автоматически |
| S6 Повторная доставка | Тот же source_id/event_id/payload дважды | Одна запись бизнес-события, одна учётная единица, повтор распознан |
| S7 Позднее событие | Событие до операции поступает после события после операции | История пересобрана, аналитика обновлена, решения сохранены |
| S8 Решение контролёра | Подтверждение, затем отклонение или дополнительная проверка | Каждое решение — новая запись; исходный сигнал сохранён; показатель пересчитан |
| S9 Несколько дефектов | Одно сообщение с двумя дефектами, позднее повторное наблюдение одного | Два различимых дефекта; повторное наблюдение не увеличивает число случаев |
| S10 Повторная обработка | Два operation_run одной операции с previous_run_id | Две работы связаны; показатель повторной обработки увеличен на один |
| S11 Интеграционная ошибка | Отправка результата и отказ эмулятора, затем ACK | Ошибка видна; повтор отправки не создаёт второго бизнес-результата |
| S12 Вмешательство | Изменение контрольной записи или шифротекста | Запись защищена от изменения либо нарушение целостности обнаружено |

Набор должен содержать несколько различных экземпляров изделий и минимум двух операторов. Для S1–S12 задать вход, порядок подачи, ожидаемые статусы, показатели и контрольные команды.

Базовый эталонный набор проектируется с четырьмя item_id: I-001 — нормальное изготовление; I-002 — входной дефект, подтверждённый контролёром, после чего изделие изолировано до решения; I-003 — новый дефект после операции, подтверждённый контролёром; I-004 — контроль с unable_to_assess. В совокупности набор охватывает два участка и двух операторов; не каждое изделие обязано проходить все участки. После применения только этих четырёх сценариев ожидаются: 3 проверенных изделия по определению раздела 7, 2 изделия с подтверждённым несоответствием, 1 изделие без пригодного результата, 1 случай входного брака, 1 случай нового дефекта. S5–S12 воспроизводятся отдельными пакетами с собственными ожидаемыми результатами; их нельзя подмешивать к базовым числам без пересчёта.

## 13. Порядок реализации с проверяемыми воротами

Ворота означают демонстрируемый результат этапа; продолжать к следующему этапу после его достижения. Оценки календарного времени не приводятся, потому что срок и состав команды не известны.

### Этап 0. Каркас и контракты

Создать структуру репозитория, README, Compose, сервер, UI, миграции, эмулятор и каталог сценариев. Определить единый набор кодов событий, статусы и матрицу ролей. Зафиксировать архитектурные решения и происхождение проектных допущений.

Готово, когда чистая машина может поднять пустую систему одной документированной последовательностью команд, а схемы событий читаются независимо от исходного кода.

### Этап 1. Приём и неизменяемый журнал

Реализовать конверт, версии, валидацию, время приёма, сохранение исходного сообщения, idempotency и конфликт повторов, карантин неизвестных/неполных сообщений. Импортировать сценарный поток.

Готово, когда S6 не удваивает запись/показатель, ошибка схемы видна с причиной, а исходный payload доступен только через разрешённый интерфейс.

### Этап 2. История изделия и порядок

Реализовать справочники, структуру сборки, связь компонентов и operation_run, полную хронологию, повторную работу, реконструкцию после позднего события и статус неопределённой связи.

Готово, когда S1, S7 и S10 показывают ожидаемую историю без потери ранних сообщений и без ручной правки БД.

### Этап 3. Контроль, случаи, причины и решения

Реализовать наблюдения трёх состояний, множественные дефекты, правила группировки, карточку случая, факты до/после, машинные события и действия, решения контролёра, историю изменений.

Готово, когда S2–S5, S8 и S9 соблюдают различие между сигналом, подтверждением, гипотезой и ошибкой оператора.

### Этап 4. Аналитика и интерфейс

Реализовать четыре основных экрана, фильтры, определения показателей, исходные основания из UI, пересчёт после решения и позднего события.

Готово, когда любой показатель из обязательного списка можно связать с конкретными записями и объяснить его изменение на S7/S8.

### Этап 5. Интеграции и защита

Реализовать входное задание эмулятора, исходящий outbox, ACK/ошибку и повтор; разграничение ролей, шифрование, защиту критических записей и показ вмешательства.

Готово, когда S11 и S12 выполняются без фиктивного обмена, исходный сигнал не изменяется решением и ключи отсутствуют в репозитории/демоданных.

### Этап 6. Архитектура, расширения и поставка

Оформить проект камер/ИИ, адаптацию к данным заказчика, интеграционные контракты, планы Kafka/OpenTelemetry и масштабирования; сделать генератор нагрузки и кодогенерацию при наличии ресурса. Завершить README, схемы, ограничения, презентацию и скринкаст.

Готово, когда другой участник может развернуть решение, запустить сценарии, сверить фактические и ожидаемые результаты и понять, какие элементы демонстрационные.

### Этап 7. Дополнительные баллы после базовой готовности

Провести сценарий 1/N обработчиков, отказ/восстановление, подключение ещё одного адаптера, автоматическую проверку контрактов. Затем, если хватает времени и подтверждена поддержка библиотеки, реализовать и показать гибридную/постквантовую защиту и ротацию профиля.

Готово, когда дополнительные материалы содержат параметры запуска, результаты, ограничения и наблюдаемые следы проверки, а не только архитектурное обещание.

Нагрузочный генератор должен принимать число изделий, источников, скорость событий, долю повторов, задержек и ошибок. Для одинакового набора сравнить 1 и несколько обработчиков: вход/с, применённые события/с, медианную и хвостовую задержку, число дублей, потерянных и ожидающих сообщений, расхождения контрольных показателей. После остановки обработчика показать восстановление и полноту обработки. Это проектный протокол измерения, без заранее выдуманных целевых чисел.

Для кодогенерации выбрать одну поддерживаемую спецификацию, зафиксировать версию инструмента и команду, перечислить генерируемые структуры/клиенты, показать изменение v1 → v2, автоматическую проверку соответствия и ситуацию, когда устаревший артефакт блокирует поставку. Моки допускаются только с явно записанными границами; ключевой двусторонний путь проверять с работающим эмулятором.

## 16. Скрипт защиты и передача результата

Базовый регламент по состоянию на экспертную сессию — 4 минуты выступления и 2 минуты вопросов; окончательный тайминг ещё обсуждается. Подготовить основной 4-минутный маршрут, резервные детали для более длинного слота и короткие ответы по архитектуре, коду, бизнес-процессу и ограничениям. Эксперты не предоставят собственный входной набор: демонстрация проходит на наших данных, методике и сценариях. Технические эксперты отдельно просмотрят заранее выгруженный код, поэтому после защиты должны воспроизводиться те же результаты без устных пояснений.

Показать подготовленные сценарии с заранее известными ожидаемыми результатами; ниже — банк шагов, который требуется смонтировать в репетиционный маршрут длительностью не более 4 минут, а не последовательность для исполнения целиком на сцене:

1. За 30–60 секунд объяснить проблему: стоимость брака и риск неверного приписывания причины, входные данные структурированы, производство закрытое.
2. Получить задание из эмулятора и показать идентификаторы изделия/сборки.
3. Запустить S1–S5, открыть хронологию и карточку нового случая, показать наблюдение, состояние до/после, журнал станка, альтернативы и неизвестное.
4. Подтвердить случай контролёром, показать отдельную запись решения, изменение двух разных счётчиков и исходящий результат с ACK.
5. Воспроизвести повтор и поздний сигнал, показать неизменность исходного сообщения, пересборку истории и отсутствие двойного учёта.
6. Попытаться изменить контрольную запись либо предъявить подготовленный изменённый пакет; показать блокировку/ошибку целостности.
7. Зафиксировать границы: камеры, аналитические модели, производственные допуски и реальные внешние системы — целевой проект, не проверенные на предприятии возможности.

Сдать код, данные/генератор, ожидаемые результаты, README с командами и версиями, схемы контрактов, архитектуру, презентацию и скринкаст. Репетиция должна проходить на чистом запуске из выгруженного репозитория, а не только в локальной среде разработчика. Если подключена внешняя CV-модель — указать источник; если обучена самостоятельно — дать ссылку на открытый датасет. При отсутствии модели этот пункт неприменим.

## 17. Решения, которые нельзя принимать без новых данных

- Точные классы дефектов, допуски, разрешение и расположение камер, задержки, пропускная способность и промышленная точность: нужны измерения на площадке.
- Реальные протоколы 1С, Галактика:ERP, MES и КОМПАС-3D, доступ и версии: нужны спецификации предприятия/вендора и среда интеграции.
- Порог уверенности автоматического вывода: нужны данные о цене ложных пропусков/ложных тревог и согласование с контролёром.
- Политика хранения, персональные данные, модель ключей и допустимые криптопрофили: нужны требования заказчика и проверка применимых норм.
- Состав команды и дедлайн: нужны для календарного плана; этот документ задаёт зависимости и ворота приёмки без выдуманных сроков.

## 18. Сквозная проверка перед показом

Проверять систему на фиксированном демонаборе после каждого изменения правил истории или статусов. Результаты хранить отдельно от входных событий. Для каждого сценария фиксировать исходный набор, команду воспроизведения, ожидаемые идентификаторы/статусы/показатели и фактический результат.

| Проверка | Доказательство |
|---|---|
| Воспроизведение | Свежий запуск по README и Compose, миграции, загрузка сценариев, скриншот/запись итоговых экранов |
| Контракты | Успех, неизвестная версия, добавленное необязательное поле, отсутствующее обязательное поле, неизвестное значение, несовместимое изменение |
| Идемпотентность | Две доставки одного события и два отправления одного результата дают один бизнес-эффект |
| Порядок | Перестановка и поздний сигнал дают ожидаемую итоговую историю по item_id |
| Неопределённость | Плохое наблюдение и ненадёжная идентификация не дают подтверждённую годность или причину |
| Решение человека | Подтверждение, отклонение и повторное решение оставляют полную цепочку исходных событий и автора |
| Аналитика | Раздельные числа дефектов/изделий, входного/производственного брака, длительностей разного происхождения |
| Интеграция | Задание/справочник получены, результат отправлен, ACK и ошибка отображены, повтор безопасен |
| Защита | Права ограничены сервером, сырьё зашифровано, ключи вне кода, вмешательство обнаружено либо запрещено |
| Расширение | Добавление второго источника или адаптера не требует изменения правил качества; описан путь Kafka/OpenTelemetry |
| Материалы | Презентация, скринкаст, схемы, ограничения и проектные предположения согласованы с текущим кодом |

Если времени на дополнительные критерии не хватает, этот набор остаётся обязательными воротами демонстрации; неподтверждённые возможности из презентации удаляются.
