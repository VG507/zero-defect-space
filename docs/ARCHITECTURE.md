# Архитектура: реализовано и целевое состояние

## Работающий путь сейчас

```text
Синтетический источник → POST /api/events → валидация → AES-GCM raw_events
                                                  ├→ processing_events / карантин
                                                  └→ cases (устойчивый ID)
                                                   → решение контролёра + outbox (одна транзакция)
                                                   → HTTP bridge → отдельный ERP-эмулятор → ACK / retry

raw_events → хронология + интервалы операций + контекст до/после → API → браузерный интерфейс
```

`raw_events` хранит исходный сериализованный JSON в шифротексте; метаданные идентичности и времени остаются открытыми для индексирования. Аутентифицированное шифрование связывает сообщение с парой `(source_id,event_id)`. Повтор с тем же содержимым не добавляет бизнес-событие, изменённый повтор попадает в `ingestion_conflicts` без замены исходного сообщения. Неверный известный конверт получает запись в `processing_events` с карантином. Применённое событие участвует в производных чтениях; карантин — нет.

Хронология сортируется по времени источника и стабильному ID, рядом показывается время приёма. `cases` фиксирует ID при первом пригодном сигнале; сигнал плохого или неизвестного качества остаётся в истории, но не создаёт подтверждаемого случая. Поздний сигнал не удаляет решение и может изменить классификацию «входной / послеоперационный»; такой случай помечается к пересмотру. Контекст показывает пригодное предшествующее наблюдение, контроль после него, предупреждения станка и действия оператора. Близость по времени не считается доказанной причиной. Человек принимает `confirmed`, `rejected` или `needs_more_inspection`; мотив, автор и каждое изменение сохраняются отдельно. В этой версии правило объединения сигналов грубое: изделие + тип + область дефекта. Его нельзя считать производственно утверждённой идентификацией одного физического дефекта.

Интервалы операции рассчитываются по `operation_run_id`. Время выполнения — от начала до конца, активное время исключает явные пары пауза/возобновление. При недостающей границе или некорректном порядке значения остаются `null`. Повторная обработка ссылается на предыдущий `operation_run_id`; повтор доставки сообщения не считается повторной обработкой.

## Граница интеграций

Эмулятор запущен отдельным HTTP-сервером: `/work-orders` отдаёт четыре задания; `/results` идемпотентно принимает результаты по `message_id`. `Bridge` переводит задание в `WorkOrderReceived`, сохраняет внешние ID и отдаёт исходящие решения. Отказ `503` фиксируется в outbox, следующий запуск `push` повторяет тот же `message_id`. Реальная конфигурация 1С/«Галактика:ERP» не известна; рабочие ручки являются только проектным примером. Перед реальным подключением требуются согласованные бизнес-объекты, протокол, схема полномочий, версионирование и испытательный контур заказчика.

## Целевое развитие и ворота доказательства

1. Перенести хранение на PostgreSQL с миграциями, ролями БД и отдельным worker; сохранить контракт event/decision/outbox. Проверить транзакции и replay после отказа.
2. Подключить edge-буфер и реальные структурированные сигналы VisionQC, OperatorVision, MachineLogs; версии схем и доверенность времени источника. Реальные камеры и CV-модель — самостоятельный проект данных, разметки, калибровки и допуска. Производственные изображения не предполагать общедоступными.
3. Расширить текущие ожидаемые контрольные точки из заданий до версионированных справочников изделия/сборки/маршрута, фонового расписания и оповещений. MVP уже разделяет `awaiting`, `missing`, `observed`, а плохое наблюдение не закрывает точку; историю `missing→resolved` проверяет тест. Необходимо отдельно проверить массовые задержки и перестройку состояния при изменении маршрута.
4. Выделить защищённый audit anchor вне основной БД и обязательный TLS/IAM для сетевого режима; сделать регламент ключей и запрет открытых токенов в UI производственной версии.
5. Описать и проверить профили адаптеров 1С, «Галактика:ERP», MES, КОМПАС-3D на доступных спецификациях, не на вымышленном совпадении форматов.
6. Измерить 1/N обработчиков, отказ и восстановление; затем выбирать Kafka/телеметрию по реальным узким местам. Отдельно выполнить генерацию контрактов и проверки несовместимости в CI. Постквантовую защиту заявлять только после конкретной работающей реализации и проверки библиотеки/модели угроз.

## Границы защиты текущего MVP

Токены ролей и ключи приходят из окружения, не находятся в коде или SQLite. Сервер по умолчанию привязан к loopback. AES-GCM обнаруживает изменение существующего шифротекста и пары идентификаторов; удаление целой записи, изменение числа записей или компрометацию ключа эта проверка не обнаруживает. SQLite/outbox не является достаточным промышленным журналом аудита. Эмулятор держит ACK в памяти, поэтому после его рестарта долговременная идемпотентность внешней стороны не гарантируется. Ни UI, ни API не должны использоваться с реальными режимными данными без отдельного допуска.
